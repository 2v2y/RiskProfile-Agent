# 五人共同验收与交接规则
文件版本：2026-08-12 19:00:15 CST

## 1. 为什么要有这份规则

“交接文件”不只是把文件发给下一个人。交出人要说明文件怎样得到，接收人要确认文件能够打开、内容和SHA-256正确，而且适合进入下一阶段。

最终每个结果都要能找到：输入文件、使用的程序和配置、版本、负责人、第二核对人和已知问题。

## 4. 一次完整交接怎样做

### 4.1 交出人要做七件事

1. 把文件放到固定目录；
2. 自己确认能够打开；
3. 记录文件名、版本、路径、行数或页数；
4. 记录输入、程序、配置和SHA-256；
5. 写清用途、使用限制和已知问题；
6. 在 `../记录表/文件交接.csv` 新增一行；
7. 保留旧版本和问题证据，不偷偷删除。

### 4.2 接收人要做七件事

1. 核对文件路径和名称；
2. 核对行列数、日期范围或页数；
3. 重新计算SHA-256；
4. 随机抽查至少一个关键数字；
5. 检查文件是否含不应分享的信息；
6. 判断已知问题会不会阻止下一阶段；
7. 在交接表填写“通过”或“不通过”并说明原因。

发现问题不能直接修改上游文件，要登记并退回原负责人。

## 5. 问题怎样处理

每个问题都要有唯一编号，并完成这条流程：

```text
发现问题 → 登记 → 停止受影响步骤 → 找到原因 → 写处理意见
→ 原负责人修正或重新运行 → 第二人复核 → 关闭问题
```

问题没有关闭时，相关数据、图表和结论不能进入下一阶段。

以下情况立即停止：

- 官方数据不完整或SHA-256变化；
- 字段解释与共同材料冲突；
- 行数无原因地改变；
- 同一样本进入两个时间部分；
- 未成熟记录被当作阴性；
- 截止时间以后的信息进入画像；
- M1和M2样本不同；
- 有人疑似提前看到Test答案；
- 正式Test已经尝试运行；
- 摘要、正文、表格和图片数字不一致。

## 7. Test开封纪律

唯一命令：

```bash
python3 程序/04_run_sealed_test.py --confirm-open-test
```

学生4运行，学生5监督，学生2复核。三人在测试开封表中分别记录：各门状态；模型、配置、程序、输入和预测SHA-256；命令与运行目录；起止时间；人员；是否首次执行；输出和SHA-256；是否报错；开封后有无方法变化。

程序会在读取答案前写 `test_open_attempt.json`。一旦该文件存在，不论之后成功或失败，本研究版本都不能第二次运行04，不能删除attempt、答案、预测或结果后重试。

失败时保留错误，正式状态写“Test开封失败、无正式Test结论”。如需再次评价，只能建立新的研究版本、使用新的未来Test时间段并重新完成全部预先登记，不能覆盖本版本。

## 8. 论文数字和图表怎样验收

每个稿件数字都要回答：来源文件是什么；在第几行第几列；是什么单位；是一个分数、百分比、差值还是区间；分母是什么；谁第一次核对；谁第二次核对；摘要、正文、表格和图片是否一致。

每张图都要保存作图数据，每张表都要可编辑，不能用截图代替。找不到来源的数字从稿件删除。

## 10. 作者贡献和最终口头验收

每名学生在 `../记录表/作者贡献记录.csv` 只登记实际完成的数据处理、程序运行、分析、图表、写作、修改和核对工作。被分配任务不等于已经完成贡献，不能代签。

最终每个人都要能回答：

1. 我的输入来自哪里；
2. 我按哪份规则做了什么；
3. 我的输出放在哪里、交给谁；
4. 我怎样证明结果正确；
5. 我发现并处理了什么问题；
6. 我负责论文的哪段、哪张表或哪幅图；
7. 我的结果不能解释成什么。

五人还要共同演示：从 `结果数字索引.csv` 找到原始结果，再找到摘要或正文中的同一个数字。
