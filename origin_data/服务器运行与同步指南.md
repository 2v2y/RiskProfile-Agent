# RiskProfile-Agent 服务器运行与 GitHub 同步指南

本文件整理项目在服务器上运行、更新和排查问题的常用操作，供以后复现和交接使用。

## 一、GitHub 与服务器如何同步

### 1. 本地改动后推送到 GitHub

在公司电脑的仓库目录里：

```bash
git add .
git commit -m "更新说明"
git push origin main
```

如果当前分支不是 `main`，按实际分支名执行，例如：

```bash
git branch
git push origin <分支名>
```

### 2. 服务器上获取最新代码

如果服务器上已经克隆过仓库，直接进目录更新：

```bash
cd ~/RiskProfile-Agent
git pull
```

如果服务器上还没有仓库：

```bash
git clone git@github.com:2v2y/RiskProfile-Agent.git
```

如果 HTTPS 克隆卡住，先测试连接：

```bash
timeout 20 git ls-remote https://github.com/2v2y/RiskProfile-Agent
```

- 有 commit 哈希输出：GitHub 通，克隆卡住一般是认证问题，改用 SSH 或 Personal Access Token。
- 无输出或超时：服务器访问不了 GitHub，改为从本地用 `scp` 传文件。

从本地传到服务器：

```powershell
scp -r "G:\Projects\intern_project\CahngeDirect_eassy\operate\stage1" root@服务器IP:/root/RiskProfile-Agent-stage1
```

### 3. 更新后注意

- `.env` 和 `runs/` 不会随 Git 上传，服务器上需要单独配置。
- 如果服务器上改过 `configs/config.json`，`git pull` 可能冲突；以 GitHub 上的新版本为准，冲突时先备份自己的 `.env`，再重新覆盖配置。
- 不要提交 SSH 密码、API Key 或 `.env` 到 GitHub。

## 二、配置 Qwen 模型

### 1. 启动 vLLM 服务

在服务器上：

```bash
conda activate test
export CC=/usr/bin/gcc
export CXX=/usr/bin/g++
export VLLM_USE_FLASHINFER_SAMPLER=0

vllm serve /DATA/models/Qwen3.8-27B \
  --served-model-name Qwen3.8-27B \
  --quantization bitsandbytes \
  --dtype bfloat16 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 8192 \
  --language-model-only \
  --enforce-eager \
  --host 0.0.0.0 \
  --port 8000 \
  2>&1 | tee /tmp/qwen38.log
```

建议用 screen 保持后台运行：

```bash
screen -S qwen
```

在 screen 里启动模型后，按：

```text
Ctrl + A
然后按 D
```

这是 detach，模型继续在后台运行。不要按 Ctrl+C，否则会停止 vLLM。

### 2. 写 `.env`

进入项目目录：

```bash
cd ~/RiskProfile-Agent/operate/stage1
```

创建 `.env`：

```bash
cat > .env <<'EOF'
QWEN_BASE_URL=http://127.0.0.1:8000/v1
QWEN_API_KEY=replace-me
QWEN_MODEL=Qwen3.8-27B
QWEN_TEMPERATURE=0
QWEN_MAX_TOKENS=2048
QWEN_TIMEOUT=120
EOF
```

注意：`QWEN_MODEL` 必须和 vLLM 实际服务名一致。如果不确定服务名，执行：

```bash
curl http://127.0.0.1:8000/v1/models
```

如果没加 `--served-model-name`，服务名可能是 `/DATA/models/Qwen3.8-27B`，那么 `.env` 里也要写这个完整路径。

### 3. 改 `configs/config.json`

要真正调用 Qwen，需要打开两个开关：

```bash
sed -i 's/"use_llm": false/"use_llm": true/' configs/config.json
sed -i 's/"provider": "dummy"/"provider": "qwen"/' configs/config.json
```

确认：

```bash
grep -n '"use_llm"\|"provider"' configs/config.json
```

正确结果：

```text
"use_llm": true
"provider": "qwen"
```

## 三、验证 Qwen 配置是否成功

### 1. 验证服务是否活着

```bash
curl http://127.0.0.1:8000/v1/models
```

有 JSON 返回 = 服务活着；连接失败 = 需要重新启动 vLLM。

### 2. 直接验证 LLM 客户端

```bash
cd ~/RiskProfile-Agent/operate/stage1

python - <<'PY'
import json
from pathlib import Path
from src.llm.client import get_llm_client

cfg = json.loads(Path("configs/config.json").read_text(encoding="utf-8"))
client = get_llm_client(cfg)
print("client:", type(client).__name__, "| model:", getattr(client, "model", ""))
print("response:", client.generate([{"role": "user", "content": "只回复OK两个字"}]))
PY
```

返回 `OK` 说明 Qwen 调用成功。如果报错，直接看报错信息，通常是模型名或地址不对。

## 五、常见问题

### 1. 测试通过但 Qwen 没跑通

测试通过代表离线逻辑正确，不等于 Qwen 调用成功。需要单独用“直接验证 LLM 客户端”命令检查真实连接。

### 2. `provider` 还是 `dummy`

说明 `configs/config.json` 没改成 `qwen`。执行上面的 `sed` 命令。

### 3. 看到三句固定模板

说明 Review 回退到了规则模板。先检查 `use_llm` 和 `provider`，再直接测 LLM 客户端。

### 4. `.env` 没生效

新版代码会自动加载 `.env`；旧版或手动运行命令时，可以先导入：

```bash
set -a
source .env
set +a
```

### 5. `final_verdict: REJECT`

REJECT 是内容审查把生成结果判定为不能通过，不代表 Qwen 连接失败。看 `audit.json` 里的 `reasons` 确认具体原因。

### 6. 克隆卡住

用 `timeout 20 git ls-remote ...` 判断是网络问题还是认证问题，再决定用 SSH、Token 还是 `scp`。
